## 1. 水平滚轮（倾斜轮 / 拇指轮）

**报告**（论坛 **poydepzaj1616**）：MX Master 3S 拇指轮绑到 **977 / 979**（水平滚动/缩放的反向版）
**没有缓动**；而同一条 977 用 **Shift+竖轮**却丝滑。

### 诊断（两条，都实测证实）

| cmd | 走**表**时的 rel | 走**名规则**时的 rel |
|---|---|---|
| 988 / 977 / 990 / 979 | **0** | **1** |

1. **同一条动作，两条规则答案不同。** `LookupAction` 命中即返回，**没设 `relativeAction`**（默认 `false`），
   而 `ClassifyName` 会按名字里的 `mousewheel` 设成 `true`。**表先试，所以表说了算** → 这些动作**要求滚轮闩锁**。
2. **`WM_MOUSEHWHEEL` 在整个 `src/` 里出现 0 次** —— 钩子只看 `WM_MOUSEWHEEL`，
   水平轮消息**不进钩子** → 闩锁**永远上不了**。

两条叠加 → 水平滚轮**必被拒**，走原生跳步。Shift+竖轮能过，因为竖轮经过钩子、上了闩。

### 做法

1. **表项静态声明 `relativeAction = true`**（`routing.h`，16 行）。
   **是不是相对动作是动作自身的属性，不该取决于"从表还是从名字找到"** —— 那个不一致就是根因。
   静态声明**零运行时开销**（网友方案是在热路径上对每条表项再查名字）。
2. **`WM_MOUSEHWHEEL` 上闩**（`GetMsgProc`）：**只做设备判定 + 上闩**，
   **不做任何表面接管**（arrange/MCP/面板/列表都不镜像 —— 那些是竖轮手势，没有实测的水平对应物）。

### ★ 关键设计：两个轮子的状态**必须分开**

`DeviceTracker` 按"最近窗口里有几种不同幅度"判定。**共用一个跟踪器会互相污染**：
竖轮发整格 `120` 清零窗口，横轮的 `15,15` 混进同一窗口 → 幅度种数 ≥ 2 → **判成触控板 → 两轮都不缓动**。

所以按轴分成两套（`g_device`/`g_deviceH`、`g_lastDevTick`/`g_lastDevTickH`、
`g_lastDevKind`/`g_lastDevKindH`、`g_wheelTick`/`g_wheelTickH`），
**过滤规则、模型、投递全部共用**（`Kick` 本来就按 `spec.axis` 选 integrator）。

### 门

`check_routes.sh` 放宽两条已记录改动（104 的 988/977 step；**126 的 rel 列 0→1**），
并新增**更强断言**：把 `rel` 列屏蔽后两文件必须**逐行相同**（借 rel 蒙混改坏 axis/delivery 会被抓）。
新增探针 `_diag/hwheel_probe.cpp` 纳入该门，断言表与名规则一致 + 钩子里确有 `WM_MOUSEHWHEEL`。

## 2. 行高补偿（"Keep size"）

**报告**（用户）：主视图**垂直滚动**按"轨道"为单位，所以**轨道放得越高滚得越远、缩得越小滚得越慢**，
反直觉。要求"缩小时补上来"。

**根因**：REAPER 的垂直滚动走**整行**，而**一行的像素高度就是缩放**。
`kVertStepsPerUnit = 1.0`（1 相对单位 = 1 行）这个固定比例就是反直觉的来源。

### 做法

```
gain = kRowRefPx / rowHeightPx ，钳到 [1, kRowGainCeiling]
kRowRefPx        = 196.0   （用户"放很大"时的实测行高 = 基准）
kRowGainCeiling  = 7.2     （= 6.0 × 1.2，用户验收的强度）
rowHeightPx      = GetMediaTrackInfo_Value(GetTrack(nullptr,0), "I_TCPH")
```

- **基准端（行高 ≥ 196px）恒为 1.0 → 用户认可的"放很大"手感逐位不变**；
- 行越矮补得越多，**上限 7.2 倍**；
- **只作用于主视图垂直滚动（989/978）**。**钢琴窗已排除**（用户要求）——
  钢琴窗的"行"是**琴键**，其高度**不跟随轨道高度**，用 `I_TCPH` 量它是错的；
- **垂直缩放不做**（缩放是倍率不是距离，增益会改变缩放速率）；水平轴也不做。

### 强度是常量，不是滑杆

曾做成滑杆（0 = 关，1.2 = 最强），用户测后要求**去掉滑杆、固定在最大**：
"一个只会被拉到最大的滑杆就不该存在"。所以机制**恒常开启**在已验收的强度。

### ⚠️ 两次失败教训（都发生在做这个功能时）

| # | 我的错误假设 | 后果 |
|---|---|---|
| 1 | `get_config_var("zoom")` 是**倍数**（默认高度 = 1.0）| 实测是 **25.8 的内部标度** → 推出的"行高" 619px → 增益被钳成 1.0 → **完全无效** |
| 2 | 基准行高 **24px**（凭空定的）| 用户真实两端是 **196px / 26px**，24 比 26 还小 → 增益全被钳掉 → **又完全无效** |

**两次都不是实现错误，是我对"输入"的假设错了**，而**探针都通过了** ——
因为探针只能验证"给定输入，算法对不对"，**验证不了"输入是不是我以为的那个东西"**。
**唯一能发现这类错误的是真实环境的一行诊断日志**（`rowgain: rowPx=… gain=…`）。

### 已知边界

**行很高时"跳得远"这一头修不了** —— 该轴**最少走一行**，一行本身就超过基准像素时，
没有可表达的更小位移。本功能只解决"缩小时变慢"。

## 3. 修复：手势末尾补发方向反了（"滚一下又弹回来"）

**报告**（用户）：`Slow step = 1`、`Ramp-up` ≈1000 及以上时，**主视图水平/垂直滚动**与
**钢琴窗垂直滚动**（三个都是 `kStepUnits`）用**最小一格**滚轮会出现"滚一下，再往回弹一下"。

**诊断（来自 DEV 投递日志，不是推理）**：

```
  n     cmd      units      topup  accum
 19    0/977    -1.0000      0    +0.49037    ← 向后发送，零头却是正的
 21    0/977    +1.0000      1    +0.00000    ← 补发反向
```

**根因**：补发的方向取自 `accum` 的符号，而 `accum` 是**取整余数** ——
发一个整单位会**冲过零**，留下**反号**的小尾巴。`Slow step = 1` 时行程太小够不到 1 单位门槛，
**全靠末尾那一次补发**，于是补成了反方向。

**做法**：`Integrator` 加 `gestureSign`（在 `Kick` 里记下**滚轮本身的方向**），
补发改用它，**不再看 `accum` 的符号**。宏的子动作同样用它。

**验证**：`_diag/topup_dir_probe.cpp` ——
日志里那个反向案例被修正；**零头与手势同向的普通情况 6 组对拍全部不变**；双向都对。
