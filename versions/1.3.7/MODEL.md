# SmoothWheelScroll for REAPER 1.3.7

**修复：MIDI 编辑器竖直滚动（音高轴）尾部的顿挫。** 只改这一个轴的投递方式，
其它一律不变。DLL md5 `383c015d8d0e0c407ad0d46194be3794`。

## 现象与定位

用户反馈：MIDI 窗**上下滚动**（不是水平缩放）收尾有回弹/顿挫感。

实测（`_diag/input_probe.cpp` 注入真实输入 + 插件日志）：

- MIDI 窗竖直滚动 = **动作 40432**（Ctrl+Alt+滚轮落在音符区，或普通滚轮落在左侧琴键）。
  两者都解析到 40432，插件都接管。
- 插件的输出**是单调的**：解码实际日志序列，同号、0 次反向。所以不是插件发了反向量。

根因：**MIDI 钢琴卷帘的竖直滚动按音高行量化（一行就是一整行）**，而本插件的fine投递
最小步进是 `1/3840 格`——**远小于一行**。行量化接收方无法表达这种碎步，只能攒够一整行
才跳一次，于是收尾那些越来越小的碎值读起来就是一顿。

对比：arrange 视图是连续的，同样的小数流在那边就是顺的（所以只有 MIDI 竖直轴有这个现象）。

## 修复（只动 MIDI 竖直轴）

给这条轴单独加一层投递规则：**按整 7 位单位发送**（不复用 `1/256` 小数）。

- 最小步进从 `1/3840 格` 变为 `1/15 格`（= 一个 7 位单位）。
- 余数仍然**跨帧累积**，所以位移总量不变。

实测总量对比（用真实模型跑，`_diag` 同款投递规则）：

| 场景 | fine 1/256（其它轴） | 整单位（MIDI 竖直） |
|---|---|---|
| 单格 | 13 次，合计 1.809 单位 | 2 次，合计 2.000 单位 |
| 10 格 @60ms | 57 次，合计 128.64 单位 | 43 次，合计 129.00 单位 |
| 10 格 @250ms | 127 次，合计 40.76 单位 | 36 次，合计 41.00 单位 |

即：**位移总量基本一致**（±5% 以内，来自取整），发送次数更少，每步更大。

## 改动范围（严格限定）

| 位置 | 是否受影响 |
|---|---|
| section 32060 的**竖直 Scroll**：40432 / 40661 | ✅ 改为整单位 |
| MIDI 编辑器**琴键**（走同一条 40432） | ✅ 同上（本来就是同一条轴） |
| MIDI 编辑器水平滚动 40433 / 40660 | ❌ 不变（仍 1/256） |
| MIDI 编辑器缩放 40430 / 40431 / 40662 / 40663 | ❌ 不变 |
| 主视图 arrange 全部（滚动/缩放） | ❌ 不变 |
| TCP / 列表 | ❌ 不变 |

判定写在 `ActionSpec::pitchQuantized`，**按 section + 轴 + "Scroll" 关键字**识别，
不写死 id，所以动作改名后仍生效（`ClassifyByName` 同步设置）。

**模型零改动**：`anim_core.h` 与 1.0.0 验收版逐字节相同；单格对拍 **1.89 / 17.94**。

## 与「参数传达原则」的关系（需要注意）

项目原则写的是「精度一律给足，不因接收方可能处理不了而降低精度」。
本次是**一处明确、有界的例外**：该轴的接收方是按行量化的，`1/3840 格` 在那里
**无法被表达**，给足精度反而产生了顿挫。因此这一轴按「该接收方表达得出的最细步进」
投递，并且**只限这一轴**，其余全部保持满精度。

（此处保留给用户验收：若手感仍不满意，可回退本版，1.3.6 不受影响。）
