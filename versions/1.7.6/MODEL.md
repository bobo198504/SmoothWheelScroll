## 1. 手势结束时的"回推一步"

**报告**（论坛 **poydepzaj1616**）：有时停下滚动时，视图会**朝反方向走一小步**。
出现在**垂直滚动、垂直缩放、水平平移**上；**水平缩放不会**。他同时给出了根因和补丁。

### 根因（他的诊断，代码核对后**完全成立**）

投递层在**手势结束时**有一个补发：**若这个手势"从未发出过一个整单位"，就补一个**，
否则慢滚一格（行程不足一个单位）在整单位接收方上会**完全不动**。

（"整单位"= 7-bit 相对单位。一格 = `kNotchUnits` = 15 单位；该补发最小步进 = 1 单位。）

它的开关是 `Integrator::sentThisBurst`，**条件是 `!sentThisBurst`**。而**宏路径**会更新这个标志，
**单动作路径**却是：

```cpp
bool sent = false;
DeliverOne(g, step, ActionSpec{g.section, g.command}, g.accum, sent);
(void)sent;                       // ← 标志被丢弃
```

**所以对每一条单动作手势，`sentThisBurst` 恒为 `false`** → **补发在每一次手势结束时都触发**，
而不是只在"真的什么都没发出去"时触发。

**补发量是"手势方向上的一个整单位"。** 而 `DeliverOne` 是**四舍五入到最近**的：
一个 0.6 的余数会发出 1、留下 **−0.4** —— 余数因此常常落在**手势的反方向**上。
补发再发一个单位，就是**停下来时那记反向的推**。

### 实测（DEV 投递日志，一格 `cmd=977`，`amount = −2.7143` 单位）

```
06.789  burst  accum=−0.46327  sent=0
06.803  replay val=127                       ← 第 1 个单位（共 4 个）
06.813  burst  accum=+0.41191  sent=1        ← sent 明明是 1，却被丢弃
06.913  replay val=127                       ← 第 2 个
07.022  replay val=127                       ← 第 3 个
07.038  replay val=127                       ← 第 4 个
07.049  top-up -> one unit BACK              ← ★ 第 5 个，且方向相反
```

**一格该走 2.71 单位，实际发了 4 个整单位，然后又倒回 1 个。**

### 修复（一行）

`src/smooth_wheel_scroll.cpp`，单动作路径：

```cpp
g.sentThisBurst = g.sentThisBurst || sent;
```

**宏路径本来就是这样写的**（`||=`）—— **只有单动作路径漏了**，这正是两条路行为不一致的原因。
改后，发过东西的手势不再被补发，那一格就交出自己的 4 个单位（= 2.71 四舍五入的结果）。

### 为什么"水平缩放不会"

补发的条件里还有 `g.delivery == Delivery::kStepUnits`（整单位接收方）。
**水平缩放是 `kStream`（满精度），根本不进这个分支** —— 与报告完全一致。
受影响的三条轴（垂直滚动 989/978、垂直缩放 1000/1001、水平平移 988/977）**都是 `kStepUnits`**。

### 范围

**只改这一处。** 投递层其它部分（`kStream` 的 1/256 网格、行高补偿、宏的
头/尾与每子动作余数、`kImmediate`、短释放的同步交付）**一律未动**。
`routing.h` 的**代码与 1.7.5 逐字节相同**，本版对它的改动**只有注释**。

## 2. 本版试过并**回退**的（记录在此，避免重复尝试）

同一天（2026-10-13）为了响应"投递层是不是做复杂了，能不能一律像触控板那样给细值"这个问题，
做了下面几组实验。**全部回退**，理由都写在代码注释里，这里只留结论。

| 实验 | 结果 |
|---|---|
| **把主视图垂直缩放改成满精度**（`kStream`）| **回退**。初次试"很顺"，用一段时间暴露出**中段停滞、不够线性**：该轴对**低于自身粒度的值不响应**，而细流让大半个手势落在那个区间里。**这就是 AGENTS 109 记录、110 回退的同一个现象** —— 本版是**重新实测**得出的，不再是沿用旧结论。**不要再凭一次短试就改这条轴。** |
| **把所有轴都改成满精度**（四条一起）| **回退**。同时暴露两个问题：**MIDI 垂直缩放变得极快**（它原来是 `kImmediate`，整个格子一次交付，改成滑行是**比看起来大得多**的改变），以及**补发失效**（见下条）。 |
| **把补发的触发条件去掉 `kStepUnits` 限制** | **回退**。一改全轴，补发的条件就永不为真，**慢滚/亚格消息彻底不动** —— 这正是补发存在的理由（见第 3 节）。 |
| **把补发的量从"1 单位"改成"carry"** | **回退**。发任意大小的余数使总量失控，用户报告"滚动和缩放乱了"。 |
| **把动画时钟换成 4ms 多媒体计时器**（与触控板的 240Hz 对齐）| **回退，而且是负优化**。UI 变重、**GPU 飙升**，且**垂直缩放的格子反而更大**：每次派发都要重绘，240 次/秒超过重绘能吸收的上限，UI 线程跟不上 → `g_tickPosted` 的"只保留一个待处理 tick"开始**丢 tick**，而 `dt` 是真实经过时间，于是下一 tick 一次交付好几个周期的位移。**模型本身与频率无关**（实测一格的 2.283063 单位在 50/64/240/1000Hz 下一致）。 |

**一句话**：**模型没问题，瓶颈在"每次派发都要重绘"这个结构上，提高频率改不了它。**

## 3. 补发是为谁存在的（本版查清，写下来备用）

补发**不是**"Slow step 设得太小"的补偿。**标准一格（120 deltas）在任何 Slow step 下都够**：

| Slow step | 一格行程 | 换算成 7-bit 单位 |
|---|---|---|
| 1（最小）| 15.28 d | **1.91 单位** |
| 5（默认）| 18.80 d | **2.35 单位** |
| 10（最大）| 23.20 d | **2.90 单位** |

**而是**：`Travel()` 的 `cap` **就是消息本身**，所以**小于 60 deltas 的消息**（自由滚轮、触控板式的高频小消息）
行程不足一个单位：

| 消息 | 行程 | 单位 | 整单位接收方 |
|---|---|---|---|
| 1–30 d | 1.0–5.75 d | **0.12–0.72** | **完全不动 → 只有补发能救** |
| 60 d | 8.30 d | 1.04 | 能动 |
| 120 d | 18.80 d | 2.35 | 能动 |

**所以补发必须保留**，而且**一旦某条轴改成 `kStream`，它的补发条件也要跟着处理** ——
不能删掉条件（亚格消息会不动），也不能发任意余数（总量失控）。
